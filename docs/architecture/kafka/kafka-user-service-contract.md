# Kafka Contract — auth-service ↔ user-service

This document describes the full messaging contract between `auth-service` (producer) and `user-service` (consumer) for the two topics that handle user lifecycle events.

---

## 1. Topics Overview

| Topic | Trigger | Producer | Consumer |
|---|---|---|---|
| `user-register-topic` | User completes OTP registration | auth-service | user-service |
| `user-update-topic` | Admin updates an account's profile | auth-service | user-service |

- **Consumer Group:** `user-service-group`
- **Kafka Mode:** KRaft (no Zookeeper), single broker (dev)

---

## 2. Topic: `user-register-topic`

### 2.1 Trigger

Fired when `AuthenticationService.verifyOtpAndRegister()` succeeds:
1. OTP is validated against the Redis cache
2. Account is created and flushed to `auth_db` via `saveAndFlush()`
3. `UserRegisteredEvent` is built and sent to the topic

### 2.2 Event Schema — `UserRegisteredEvent`

```json
{
  "accountId": "b41fac5d-aa57-461d-88f6-28192cfbd64a",
  "fullName": "Nguyen An Binh",
  "phoneNumber": "0812154005",
  "dateOfBirth": [1995, 10, 15],
  "email": "anbinh200@gmail.com",
  "gender": "MALE",
  "address": "123 Main St, City",
  "identityCard": "123456789012"
}
```

| Field | Type | Required | Constraint |
|---|---|---|---|
| accountId | UUID String | Yes | Unique, generated by auth-service |
| fullName | String | Yes | Max 50 chars |
| phoneNumber | String | Yes | `^(0|\+84)[0-9]{9,10}$` |
| dateOfBirth | `[YYYY, MM, DD]` | No | Jackson serializes `LocalDate` as an integer array |
| email | String | Yes | RFC 5322, unique in auth_db |
| gender | String | No | `MALE` \| `FEMALE` \| `OTHER` |
| address | String | No | Max 255 chars |
| identityCard | String | No | Exactly 12 digits, unique |

### 2.3 Registration Flow

```
PHASE 1 — INITIATE
Frontend → POST /api/auth/register/initiate → auth-service
  ├─ Validate email format & uniqueness
  ├─ Validate username uniqueness
  ├─ Generate 6-digit OTP
  ├─ Cache OTP in Redis (TTL 5 min)
  └─ Send OTP email

PHASE 2 — VERIFY & REGISTER
Frontend → POST /api/auth/register/verify → auth-service
  ├─ Validate OTP from Redis
  ├─ Double-check email/username uniqueness (race condition guard)
  ├─ Create Account entity
  ├─ Hash password (BCrypt)
  ├─ Set status = 1, assign ROLE_USER
  ├─ saveAndFlush() → auth_db
  ├─ Build UserRegisteredEvent
  ├─ Send to Kafka → user-register-topic
  └─ Delete OTP from Redis

PHASE 3 — ASYNC PROFILE CREATION
Kafka → user-service
  ├─ Deserialize UserRegisteredEvent
  ├─ Idempotency check: existsById(accountId)
  │   └─ If exists → log WARN, return (skip)
  ├─ Map event → User entity
  ├─ userRepository.save(user)
  └─ Log success
```

### 2.4 Consumer Idempotency

user-service calls `userRepository.existsById(accountId)` before every save.
If the accountId already exists → log a warning and return without saving. No exception, no retry.

## 3. Topic: `user-update-topic`

### 3.1 Trigger

Fired when `AccountService.updateAccount()` is called (admin updating a user's profile):
1. The account is updated in `auth_db`
2. `UserUpdatedEvent` is built from the profile fields and sent to the topic

### 3.2 Event Schema — `UserUpdatedEvent`

```json
{
  "accountId": "b41fac5d-aa57-461d-88f6-28192cfbd64a",
  "fullName": "Nguyen An Binh Updated",
  "phoneNumber": "0912345678",
  "dateOfBirth": [1995, 10, 15],
  "email": null,
  "gender": "FEMALE",
  "address": "456 New Street",
  "identityCard": "123456789012"
}
```

| Field | Type | Required | Constraint |
|---|---|---|---|
| accountId | UUID String | Yes | Must exist in user_db |
| fullName | String | No | Max 50 chars |
| phoneNumber | String | No | `^(0|\+84)[0-9]{9,10}$`, unique |
| dateOfBirth | `[YYYY, MM, DD]` | No | — |
| email | String | No | Not used for profile update at this time |
| gender | String | No | `MALE` \| `FEMALE` \| `OTHER` |
| address | String | No | Max 255 chars |
| identityCard | String | No | Exactly 12 digits |

### 3.3 Update Flow

```
Admin → PUT /api/accounts/{accountId} → auth-service
  ├─ Lookup Account by accountId (throw 404 if not found)
  ├─ Update account fields (email, password, roles)
  ├─ Re-hash password if a new password is provided
  ├─ accountRepository.save(account)
  ├─ Build UserUpdatedEvent from profile fields
  └─ Send to Kafka → user-update-topic

Kafka → user-service
  ├─ Deserialize UserUpdatedEvent
  ├─ Check existsById(accountId)
  │   └─ If NOT exists → log WARN, return (profile not yet created)
  ├─ Build UserUpdateRequest from event
  ├─ Validate phone uniqueness (if phone number changed)
  ├─ userMapper.updateUser(request, user)
  ├─ user.setUpdatedAt(LocalDateTime.now())
  ├─ userRepository.save(user)
  └─ Log success
```

## 4. Kafka Configuration

### 4.1 Producer — auth-service (`application.yml`)

```yaml
spring:
  kafka:
    bootstrap-servers: ${SPRING_KAFKA_BOOTSTRAP_SERVERS:localhost:9092}
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      properties:
        "[spring.json.add.type.headers]": true
        "[spring.json.type.mapping]": "userRegistered:authservice.event.UserRegisteredEvent,userUpdated:authservice.event.UserUpdatedEvent"
```

### 4.2 Consumer — user-service (`application.yml`)

```yaml
spring:
  kafka:
    bootstrap-servers: ${SPRING_KAFKA_BOOTSTRAP_SERVERS:localhost:9092}
    consumer:
      group-id: user-service-group
      auto-offset-reset: earliest
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        "[spring.deserializer.value.delegate.class]": org.springframework.kafka.support.serializer.JsonDeserializer
        "[spring.json.trusted.packages]": "*"
        "[spring.json.use.type.headers]": true
        "[spring.json.type.mapping]": "userRegistered:userservice.event.UserRegisteredEvent,userUpdated:userservice.event.UserUpdatedEvent"
```

> **Why `ErrorHandlingDeserializer`?**
> It wraps `JsonDeserializer` so that when a message has no type header (e.g. messages produced before type headers were enabled), the consumer delivers `null` instead of crashing. The listener handles `null` with an early return, allowing the offset to advance past the poison message.

> **Why type mapping aliases instead of full class names?**
> The two services use different packages (`authservice.event.*` vs `userservice.event.*`). Short aliases (`userRegistered`, `userUpdated`) are resolved independently by each service's mapping, avoiding `ClassNotFoundException` on the consumer side.

### 4.3 Message Header

Every Kafka message produced by auth-service carries:

| Header | Value (register topic) | Value (update topic) |
|---|---|---|
| `__TypeId__` | `userRegistered` | `userUpdated` |

## 5. Validation Responsibilities

| Rule | auth-service | user-service | Notes |
|---|---|---|---|
| Email format | ✅ | ❌ | Validated at the REST layer |
| Email unique | ✅ | ❌ | Checked before account creation |
| Username unique | ✅ | ❌ | Checked before account creation |
| Phone format | ✅ (register) | ❌ | Validated at the REST endpoint |
| Phone unique (update) | ❌ | ✅ | user-service checks before save |
| Identity card — 12 digits | ✅ (register) | ❌ | Validated at the REST endpoint |
| OTP valid | ✅ | ❌ | Redis TTL 5 min |
| Idempotency (register) | ❌ | ✅ | `existsById(accountId)` before save |
| Profile exists (update) | ❌ | ✅ | `existsById(accountId)` before update |

## 6. Error Handling

### Producer (auth-service)

| Scenario | Action |
|---|---|
| OTP invalid | Throw `INVALID_OTP`, rollback transaction, NO Kafka message sent |
| Account save fails | Rollback transaction, NO Kafka message sent |
| Kafka send fails | Log error (fire-and-forget — does not block the HTTP response) |

### Consumer (user-service)

| Scenario | Action |
|---|---|
| Message has no type header (legacy message) | `ErrorHandlingDeserializer` delivers `null` → `if (event == null) return` |
| accountId not found in user_db (update) | Log WARN, skip |
| accountId already exists in user_db (register) | Log WARN, skip (idempotency) |
| Phone number already taken (update) | Throw `PHONE_EXISTED`, exception is logged |
| Unexpected exception | Log error, throw `RuntimeException` to trigger Kafka retry |

## 7. Kafka CLI — Debug Commands

Run from inside the Kafka container:

```bash
docker exec -it kafka bash

# List all topics
kafka-topics.sh --list --bootstrap-server localhost:9092

# Inspect topic configuration
kafka-topics.sh --describe --topic user-register-topic --bootstrap-server localhost:9092
kafka-topics.sh --describe --topic user-update-topic --bootstrap-server localhost:9092

# Read all messages from the beginning
kafka-console-consumer.sh --topic user-register-topic --bootstrap-server localhost:9092 --from-beginning
kafka-console-consumer.sh --topic user-update-topic --bootstrap-server localhost:9092 --from-beginning

# Check consumer group lag
kafka-consumer-groups.sh --describe --group user-service-group --bootstrap-server localhost:9092

# Skip stuck/poison messages by resetting offset to latest
kafka-consumer-groups.sh --group user-service-group --topic user-update-topic \
  --reset-offsets --to-latest --execute --bootstrap-server localhost:9092
```

## 8. Troubleshooting

| Symptom | Root Cause | Fix |
|---|---|---|
| Consumer loop error: `No type information in headers` | Legacy message in the topic was produced without a `__TypeId__` header | `ErrorHandlingDeserializer` handles this — message is skipped and offset advances |
| `ClassCastException` in consumer | `spring.json.use.type.headers: false` caused all messages to be deserialized as the same default type | Enable `use.type.headers: true` and configure `type.mapping` |
| Account update not reflected in user_db | Consumer silently dropping the event | Check consumer group lag; inspect user-service logs for deserialization errors |
| Duplicate user profile | Missing idempotency check | `existsById(accountId)` must be called before every `save()` |
| Consumer lag keeps growing | Consumer is slow or throwing repeated exceptions | Check user-service error logs |
