# Kafka Contract Specification - User Registration

## Mục tiêu
Tài liệu này mô tả contract (giao tiếp) giữa `auth-service` (producer) và `user-service` (consumer) cho luồng sự kiện đăng ký user thành công.

- **Producer:** `auth-service`
- **Consumer:** `user-service`
- **Topic:** `user-register-topic`
- **Consumer Group:** `user-service-group`

---

## 1. Message Payload Specification

### 1.1 JSON Format
```json
{
  "accountId": "b41fac5d-aa57-461d-88f6-28192cfbd64a",
  "fullName": "Nguyen An Binh",
  "phoneNumber": "0812154005",
  "dateOfBirth": [1995, 10, 15],
  "email": "anbinh200@gmail.com",
  "gender": "MALE",
  "address": "123 Main St, City",
  "identityCard": "123456789012"
}
```

### 1.2 Field Definitions

| Field | Type | Required | Constraint |
|-------|------|----------|-----------|
| accountId | UUID String | Yes | Unique, generated by auth-service |
| fullName | String | Yes | Max 255, alphanumeric + space |
| phoneNumber | String | Yes | "0" + 9-10 digits |
| dateOfBirth | Array[int] | Yes | [YYYY, MM, DD] format |
| email | String | Yes | RFC 5322, max 255, unique |
| gender | String | Yes | MALE \| FEMALE \| OTHER |
| address | String | No | Max 500 chars |
| identityCard | String | No | Exactly 12 digits, unique |

## 2. Auth-Service (Producer) Specification

### 2.1 Responsibilities
- Validate toàn bộ dữ liệu đầu vào (email format, phone format, CCCD digits, uniqueness)
- Verify OTP từ Redis (TTL 5 minutes)
- Create Account entity mới
- Hash password
- Assign default role (ROLE_USER)
- Persist Account vào auth_db
- Build UserRegisteredEvent từ Account data
- Send event sang Kafka topic user-register-topic
- Clean up OTP từ Redis

### 2.2 Validation Rules (Auth-Service must validate)
- ✅ Email format hợp lệ (RFC 5322)
- ✅ Email unique trong auth_db
- ✅ Username unique
- ✅ Phone number: "0" + 9-10 digits
- ✅ Identity Card: exactly 12 digits (nếu có)
- ✅ Full name: not empty
- ✅ Password: 8+ chars, upper/lower/digits/special chars
- ✅ OTP valid: match cached OTP in Redis
- ✅ OTP not expired: TTL 5 minutes

### 2.3 Registration Flow
**Step 1 - Initiate Registration:**
- Receive RegisterRequest (email, username, password, fullName, phoneNumber, dateOfBirth, gender, address, identityCard)
- Validate email format
- Check email not exist
- Check username not exist
- Generate OTP (6 digits random)
- Store OTP in Redis with TTL 5 minutes
- Send OTP via email to user

**Step 2 - Verify OTP & Register:**
- Receive VerifyOtpRequest (RegisterRequest + OTP input)
- Validate OTP against Redis cached value
- Double-check email/username not exist (race condition prevention)
- Create Account entity
- Hash password using BCrypt/Argon2
- Set status = 1 (active)
- Assign ROLE_USER default role
- Persist Account (flush immediately)
- Build UserRegisteredEvent from Account
- Send event to Kafka topic user-register-topic
- Delete OTP from Redis
- Return AccountResponse with JWT token

### 2.4 Kafka Producer Config
- Topic: user-register-topic
- Serializer: JsonSerializer (value)
- Acks: all (ensure write before return)
- Retries: 3 (auto-retry if broker unavailable)
- Batch size: 16384 bytes
- Linger time: 10ms

### 2.5 Error Handling
- Kafka send fail: log error, throw exception to client
- Account creation fail: rollback transaction, return error
- OTP invalid: throw INVALID_OTP exception
- Duplicate user: throw USERNAME_EXISTED/EMAIL_EXISTED exception

## 3. User-Service (Consumer) Specification

### 3.1 Database Requirements
Table: `users` (or `user_profiles`)
- userId (UUID, primary key, auto-generated)
- accountId (UUID, unique not null, FK reference)
- fullName (String, not null, max 255)
- phoneNumber (String, not null, max 20)
- dateOfBirth (LocalDate, nullable)
- email (String, not null, unique, max 255)
- gender (String, nullable, max 10)
- address (String, nullable, max 500)
- identityCard (String, nullable, unique, max 20)
- createdAt (Timestamp, auto-set @PrePersist)
- updatedAt (Timestamp, auto-set @PreUpdate)
- status (Integer, default 1)

### 3.2 Domain Objects Required
- **UserRegisteredEvent DTO:** deserialize from Kafka message
  - Fields: accountId, fullName, phoneNumber, dateOfBirth, email, gender, address, identityCard
  - Use Lombok: @Data, @Builder, @NoArgsConstructor, @AllArgsConstructor

- **User Entity:** JPA mapping to users table
  - All fields from table schema
  - Implement @PrePersist/@PreUpdate

### 3.3 Repository Methods
- `Optional<User> findByAccountId(String accountId)`
- `boolean existsByAccountId(String accountId)`
- `boolean existsByEmail(String email)`
- `Optional<User> findByEmail(String email)`

### 3.4 Consumer Responsibilities
- Listen on topic user-register-topic, group user-service-group
- Deserialize message to UserRegisteredEvent
- Check idempotency: if accountId exists → skip (log warning)
- Map event → User entity
- Persist User to user_db
- Acknowledge message on success
- Handle errors gracefully (log, retry, DLT)

### 3.5 Kafka Consumer Config
- Topic: user-register-topic
- Group ID: user-service-group
- Deserializer: JsonDeserializer (value)
- Auto offset reset: earliest
- Session timeout: 30s
- Heartbeat interval: 10s
- Ack mode: manual (acknowledge after save success)
- Trusted packages: userservice.* (for security)

### 3.6 Jackson Configuration
- Support deserialization of dateOfBirth [YYYY, MM, DD] → LocalDate
- Enable JavaTimeModule in ObjectMapper
- Config: `write-dates-as-timestamps: false`
- Config: `fail-on-unknown-properties: false`

### 3.7 Consumer Logic
1. Receive UserRegisteredEvent
2. Log: "Received user registration event for Account ID: {accountId}, Partition: {p}, Offset: {o}"
3. Check idempotency: `if (repo.existsByAccountId(accountId)) { skip and log warning }`
4. Map event → User entity
5. Call `repo.save(user)`
6. Log: "Successfully created user profile for Account ID: {accountId} with User ID: {userId}"
7. Acknowledge message
8. On exception: log error, do NOT acknowledge (let Kafka retry)

### 3.8 Idempotency Pattern
- Before save: always check `existsByAccountId(accountId)`
- If exists: log warning, acknowledge message, skip save
- Purpose: handle duplicate messages from Kafka broker

### 3.9 Error Handling
- DB constraint violation: log error, throw exception, NOT acknowledge
- Deserialization error: log error, send to DLT, acknowledge
- Network timeout: log error, NOT acknowledge (Kafka retry)
- Unexpected exception: log error, NOT acknowledge (Kafka retry)

## 4. Validation & Business Rules

### 4.1 Responsibility Matrix

| Rule | Auth-Service | User-Service | Notes |
|------|--------------|--------------|-------|
| Email format valid | ✅ Yes | ❌ No | Auth validates |
| Email unique | ✅ Yes | ❌ No | Auth validates |
| Phone format valid | ✅ Yes | ❌ No | Auth validates |
| CCCD 12 digits | ✅ Yes | ❌ No | Auth validates |
| Username unique | ✅ Yes | ❌ No | Auth validates |
| Idempotency check | ❌ No | ✅ Yes | By accountId |
| Handle duplicates | ❌ No | ✅ Yes | Skip if exists |

### 4.2 Key Business Rules
- No duplicate processing: user-service checks idempotency by accountId
- Data trust: user-service trusts auth-service validation
- Separation of concerns: auth validates, user-service persists
- Eventual consistency: user profile created async after account
- Message reliability: Kafka acks=all, replication factor ≥ 1

## 5. Data Flow & Sequence

```
PHASE 1: INITIATE REGISTRATION
Frontend → POST /auth/register → Auth-Service
  ├─ Validate email, username
  ├─ Generate OTP
  ├─ Store in Redis (TTL 5min)
  └─ Send email

PHASE 2: VERIFY OTP & REGISTER
Frontend → POST /auth/verify-otp → Auth-Service
  ├─ Validate OTP
  ├─ Create Account
  ├─ Hash password
  ├─ Save to auth_db
  ├─ Build event
  ├─ Send to Kafka
  └─ Delete OTP

PHASE 3: ASYNC PROFILE CREATION
Kafka topic (user-register-topic) → User-Service
  ├─ Check idempotency
  ├─ Map event → entity
  ├─ Save to user_db
  └─ Acknowledge

CASE: DUPLICATE MESSAGE
Kafka resends → User-Service
  ├─ Check idempotency: YES exists
  ├─ Skip save
  └─ Acknowledge (no save)
```

## 7. Error Scenarios

### Producer-Side Failures

| Scenario | Action | Result |
|----------|--------|--------|
| Account save fails | Rollback transaction | 500 error to client, NO Kafka message |
| OTP invalid | Throw exception | 400 error, can retry |
| Kafka unavailable | Retry 3x, then throw | 500 error to client |

### Consumer-Side Failures

| Scenario | Action | Result |
|----------|--------|--------|
| Deserial fail | Log error, send to DLT | Message acknowledged |
| DB save fails | Log error, NOT ack | Kafka retries |
| Duplicate accountId | Log warn, skip | Message acknowledged (idempotency) |
| DB constraint error | Log error, NOT ack | Kafka retries or DLT |
| Network timeout | Log error, NOT ack | Kafka retries |

### Dead Letter Topic (DLT)
- Optional but recommended
- Topic: user-register-topic.DLT
- Messages after max retries (default 3) go to DLT
- Operations team monitors for manual intervention

## 12. Troubleshooting

| Issue | Cause | Solution |
|-------|-------|----------|
| Consumer not receiving | Bootstrap server disconnected | Check kafka:9092 connectivity |
| Deserialization error | dateOfBirth format mismatch | Enable JavaTimeModule, verify trusted.packages |
| Duplicate profiles | Missing idempotency check | Verify existsByAccountId() before save |
| Message loss | acks != all | Set acks=all, replication factor ≥ 2 |
| Lag increasing | Consumer slow | Increase partitions, optimize save |
| OTP expires early | TTL too short | Set Redis TTL ≥ 5 minutes |
| Infinite retries | Max retries unconfigured | Configure max retry backoff, enable DLT |

## 12. Common Issues & Solutions

| Issue | Cause | Solution |
|-------|-------|----------|
| Consumer không nhận message | Kafka bootstrap server không kết nối | Kiểm tra `spring.kafka.bootstrap-servers` config |
| Deserialization lỗi | Class path không đúng | Đảm bảo `spring.json.trusted.packages` config |
| Duplicate user profile | Consumer xử lý message 2 lần | Implement idempotency với `existsByAccountId()` |
| Message mất | Producer không ghi được | Config `acks: all` để đảm bảo |
| Consumer offset lag | Consumer chạy chậm | Tăng `--consumer.max.poll.records` |
